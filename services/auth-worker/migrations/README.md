# D1 migrations

Migration 0000_auth_worker_internal_config.sql creates the private Worker bootstrap-state table used to make first-party OAuth client registration idempotent.

Migration 0001_better_auth.sql is exported by the isolated local Worker through Better Auth's supported getMigrations() API. The generator endpoint is protected by a random bearer secret and requires ALLOW_SCHEMA_BOOTSTRAP=true. It must never be enabled on a shared or production environment.

Migration 0002_seed_first_party_oauth_client.sql provisions the one fixed first-party public OIDC client and resource. It has no client secret, only the exact HTTPS SPA callback, and the authorization_code grant with PKCE required. The internal client-bootstrap endpoint only verifies these seed rows; it does not create OAuth clients.

The generated Better Auth output must include core Better Auth tables, JWKS storage, all OAuth Provider tables, and the database-backed rate-limit table. Custom tables from migration 0003 are excluded from the Better Auth schema export. Do not hand-write a partial Better Auth schema.

Review the generated SQL and verify it against disposable local D1. The PR validation workflow applies migrations 0000–0003, runs the full email/session/OAuth/PKCE/JWT integration suite, and commits the generated 0001 SQL and matching npm lockfile only after the entire pipeline passes. The checked-in lockfile is installed with npm ci. Never generate schema against a remote or production D1 database. Do not apply migrations to production.

Migration 0001 remains the immutable initial Better Auth core schema. Registration metadata columns `accountType`, `username`, and `referralCode` are introduced by additive migration 0004, because the original 0001 has already been applied to the remote staging D1. The generator explicitly strips these three extension columns from the regenerated 0001 output so local tests and remote migration history remain consistent. These attributes are registration inputs only; they are not authentication roles or authorization claims.


Migration 0003 creates the encrypted ZeptoMail Agent profile store, the selected active Agent pointer, and an admin test-email rate limit. Send Mail Tokens are encrypted by the Worker with AES-256-GCM using the `AUTH_EMAIL_ENCRYPTION_KEY` Worker secret. This key must be stable across deployments; changing it without re-encrypting saved profiles makes existing tokens unreadable. Never export the ciphertext or key to frontend code.

Only the authenticated active-admin API can create, rotate, activate, test, or remove Agent profiles. The API returns metadata and a tokenConfigured flag only—never a token or ciphertext.

Migration 0005 (`0005_telegram_phone_verification.sql`) creates a short-lived, one-use challenge table for the optional Telegram OIDC **phone-verification step**. It is not a Telegram login provider and must only be started for an already authenticated Better Auth session. The table stores a SHA-256 hash of the random OAuth state, the Better Auth user UUID, nonce, PKCE verifier and timestamps; it does not store a phone number, Telegram access token or ID token. Expired challenges are pruned on challenge creation, the per-user 60-second start cooldown is reserved atomically, and callbacks consume the challenge with one atomic `DELETE ... RETURNING`.

The Worker verifies the Telegram ID token signature against Telegram's JWKS and validates the exact issuer, audience, nonce, expiry and `phone_number_verified=true` claim before projecting only the legacy-compatible SHA-256 hash of the international phone digits to the server-only Supabase RPC. The raw phone number and provider tokens must never be logged, returned to the browser, or persisted in D1/Supabase.

The guarded staging D1 migration workflow is versioned for migrations 0000–0006 and checks reviewed SHA-256 values for 0004, 0005 and 0006, the exact non-production D1 name/UUID, and the expected 18-table schema after apply. As of 7 November 2026, remote staging D1 has migrations 0000–0006 applied and all 18 expected tables verified, including `auth_phone_verification_challenges` and `auth_email_accounts.provider`. Do not rerun already-applied migrations. Future D1 changes must use a new migration number and a reviewed checksum. This is not a production migration. Telegram verification remains disabled until BotFather app registration/callback allowlisting and a real hosted consent/callback test pass.

Provisioning destination isolation: the Worker keeps `SUPABASE_URL` for the temporary legacy Admin-session bridge only. Better Auth identity, email-verification and Telegram phone-verification RPCs use `SUPABASE_PROVISIONING_URL` exclusively. In this migration branch that origin is hard-pinned in `wrangler.toml` and code to the isolated Free staging project `https://ydamszdfsxqisanazdkb.supabase.co`; the production project is explicitly rejected, and there is no fallback to `SUPABASE_URL`. `SUPABASE_PROVISIONING_ENABLED` stays unset until the owner installs the staging-only service-role secret and approves hosted staging acceptance. Never set it to true while provisioning URL or service-role credentials point anywhere other than the isolated staging project.

Migration 0006 (`0006_transactional_email_provider.sql`) adds a constrained `provider` column to `auth_email_accounts`, with `zeptomail` as the default. This is additive: existing encrypted ZeptoMail Agent rows keep their existing ciphertext and remain ZeptoMail; no credential is decrypted, re-encrypted, deleted, or copied. New accounts may use `brevo` or `zeptomail`.

The managed email dispatcher reads the currently active account from D1 and decrypts its credential only in the Worker. Brevo uses an API Key v3, ZeptoMail uses an Agent Send Mail Token; both are stored in the existing AES-256-GCM ciphertext column and never returned by the admin API. The Admin test action sends only to the authenticated admin's own email and remains limited to one test per minute.

The earlier free-first recommendation (Brevo Free) is superseded by the 8 November 2026 product decision: **ZeptoMail is the default provider for new Agent profiles**, while Brevo Free remains available as a fallback that can be selected without a Worker redeploy. ZeptoMail uses a credit/pay-as-you-go model; do not enable auto top-up or purchase credits without the owner's explicit choice. If the operating constraint returns to strictly zero-cost email, select the Brevo Free Agent instead. This UI default does not create an account, activate a sender, or incur a charge. See the [Brevo Free plan limit FAQ](https://help.brevo.com/hc/en-us/articles/208580669-FAQs-What-are-the-limits-of-the-Free-plan) and [ZeptoMail credit model](https://www.zoho.com/zeptomail/subscription.html).

The staging Worker uses `AUTH_EMAIL_PROVIDER=managed`. Until an active provider account has been saved and selected in Admin → Settings → Transactional Email, registration verification and password-reset delivery intentionally fail closed rather than falling back to an unconfigured or paid provider. No provider API key is committed to Git or added as a Worker secret; the admin enters it through the authenticated Admin panel and the Worker encrypts it before storage.

The 18-table schema, seven Better Auth registration columns, Telegram challenge table and `auth_email_accounts.provider` column were checked after application. These are changes to the isolated Free D1 only; no production D1 exists or was touched.

The provider-aware Worker source was deployed to staging by [run #42339805803](https://github.com/taufx98/sykabelajar4.0/actions/runs/42339805803). It runs with `AUTH_EMAIL_PROVIDER=managed`. It remains unable to send signup/reset mail until an owner verifies the sender domain and adds/activates a Brevo Free API Key through the staging Admin panel. The Worker deliberately does not fall back to paid ZeptoMail or an unconfigured webhook.


Migration 0007 (`0007_managed_social_login_providers.sql`) adds D1-backed Google/Facebook/X provider configuration metadata and encrypted client-secret storage. The ciphertext uses the dedicated Worker secret `AUTH_PROVIDER_ENCRYPTION_KEY`, with AES-256-GCM and a separate domain-separated key derivation; it must never reuse `AUTH_EMAIL_ENCRYPTION_KEY`. The Worker returns no client secret through Admin GET responses. The first Admin save seeds any existing Worker environment provider pairs into the encrypted D1 store, makes managed settings authoritative, and increments the config revision so the Worker rebuilds the Better Auth instance without deployment. Facebook and X remain disabled by default; Google is enabled on first credential save unless the admin explicitly disables it. The login UI only displays providers that the public metadata endpoint reports as configured and enabled.

Migration 0007 creates schema only; it does not seed user accounts, OAuth credentials, enable a provider, or change the live Worker. Its application uses the same exact staging-D1 guard and no Worker deployment. A stable `AUTH_PROVIDER_ENCRYPTION_KEY` secret is required before an Admin can save provider credentials. Never paste the key or OAuth client secrets into chat, frontend environment variables, or source control. Instagram consumer login is intentionally unsupported; Telegram remains a separate phone-verification flow.


### 8 November — no legacy account migration

The owner confirmed that every user starts with a fresh Better Auth account. No Supabase Auth emails, password hashes, provider identities, sessions, phone/email verification state or profile metadata are migrated. The Stage 3 Postgres identity root distinguishes new accounts with identity_origin='better_auth' from UUID-only legacy_reference tombstones generated solely from still-referenced application FK columns. The tombstones protect the 69 existing FK relationships but are not accounts and cannot authenticate. The identity draft retires the three legacy Auth signup/referral triggers, while the RLS issuer draft accepts only the Better Auth issuer. Stage 6 remains responsible for any approved cleanup of old accounts and dependent application data.


### 8 November — staging managed social-login schema

The guarded Cloudflare staging D1 workflow applied migration 0007 to the fixed non-production database `sykabelajar-auth-poc`. Remote verification passed for the two managed social-provider tables and their expected columns; all 20 D1 tables and seven registration fields were present. The migration seeded only the single metadata row (`managed_mode=0`), not provider credentials or user accounts. The Worker was then deployed and the hosted OIDC/JWKS smoke test passed. Production resources were not targeted.
